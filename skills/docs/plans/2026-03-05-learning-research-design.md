# 학습용 리서치 스킬 설계: learning-research

**설계일**: 2026-03-05
**목적**: 특정 주제를 깊이 이해하기 위한 학습 자료 수집 및 체계적 정리
**기반**: 기존 `research` 스킬의 병렬 전문가 프로세스 재활용

---

## Overview

기존 `research` 스킬이 "의사결정을 위한 자료 수집"이라면, `learning-research`는 "주제를 깊이 이해하기 위한 학습 자료 수집 및 이해도별 정리"에 특화된 스킬이다.

병렬 전문가 서브에이전트로 자료를 수집하고, 모드에 따라 논리 흐름(study) 또는 이해도 계층(deep-study)으로 정리한 학습 노트를 생성한다. 출력물은 Obsidian vault에 자동 저장된다.

---

## Key Requirements

1. 두 가지 모드: `study` (가벼운 논리 흐름 정리) / `deep-study` (3계층 심층 정리)
2. 학습 목적에 특화된 전문가 6종 (기존 research와 별개)
3. Obsidian vault 자동 저장 (fallback: `docs/study/`)
4. 카테고리 자동 분류
5. Codex 독립분석 포함

## 입력 요구사항

조사 시작 전 반드시 3가지 확인:

1. **Topic**: 학습할 주제 (예: "Transformer 아키텍처", "Kubernetes 네트워킹")
2. **Purpose**: 왜 배우는가 (예: "업무 적용", "면접 준비", "순수 호기심", "기초 다지기")
3. **Mode**: 학습 깊이
   - `study`: 논리 흐름 정리 (개념 → 왜 → 어떻게 → 한계/대안). 전문가 3개
   - `deep-study`: 3계층 정리 (입문 → 중급 → 심화). 전문가 6개 전원

Mode 미지정 시 주제 복잡도를 판단해서 추천하되, 사용자에게 확인 후 진행.

## 전문가 유형 (6종)

| 전문가 | 역할 | 주요 소스 | study | deep-study |
|--------|------|----------|:-----:|:----------:|
| **개념/이론** | 핵심 개념, 용어 정의, 원리 설명 | 위키, 교과서적 자료, 공식 docs 개념 섹션, MDN | O | O (입문) |
| **역사/맥락** | 왜 등장했는가, 어떤 문제를 해결하는가 | 창시자 글, 역사적 배경 글, 초기 논문/RFC | - | O (입문) |
| **구조/동작원리** | 내부 아키텍처, 동작 메커니즘, 데이터 흐름 | 공식 docs, 설계 문서, 소스코드 분석 글, 아키텍처 다이어그램 | O | O (중급) |
| **실습/튜토리얼** | 따라하며 배울 수 있는 자료 | 공식 튜토리얼, 코드랩, 강의, 예제 프로젝트, YouTube | - | O (중급) |
| **심화/엣지케이스** | 고급 패턴, 함정, 성능 이슈, 내부 구현 | 논문, 심층 블로그, 소스코드, 디버깅 사례, 컨퍼런스 발표 | - | O (심화) |
| **생태계/연관지식** | 관련 기술, 대안, 선수 지식, 학습 로드맵 | 비교 글, 로드맵, 커뮤니티 추천, awesome-* 리스트 | O | O (전 계층) |

각 전문가는 독립된 에이전트 파일(`agents/*.md`)로 관리.

## 워크플로우

### Step 1: 주제 분석 및 전문가 할당

입력 3가지(Topic, Purpose, Mode) 확인 후:

1. 주제를 핵심 키워드 3-5개로 분해
2. 카테고리 자동 분류 (AI, DevOps, Backend, Frontend, Database, Security, Network 등)
3. Mode에 따라 전문가 수 결정 (study: 3개, deep-study: 6개)
4. 각 전문가에게 구체적 담당 범위 할당

사용자에게 할당 계획 고지:
```
[주제] 학습 자료를 수집합니다.
모드: study / deep-study
카테고리: [자동 분류 결과]
투입 전문가: [목록]
저장 위치: study/YYYY/MM/<category>/<mode>/<topic>.md
```

### Step 2: 병렬 조사 실행

모든 전문가를 동일 턴에 동시 스폰. 각 전문가에게 전달:

```
역할: [전문가 유형]
학습 주제: [원본 주제]
담당 범위: [구체적 할당 영역]
지침 파일: agents/[파일명].md

반환 형식:
- 핵심 발견사항 (3-5개)
- 레퍼런스 (URL, 출처, 발행일)
- 인사이트
- 불확실하거나 미확인된 항목
```

Codex 독립분석도 동시 실행 (`codex-synthesis.md`의 research 프롬프트 템플릿 사용).

### Step 3: 결과 수집 및 교차 검증

모든 전문가 + Codex 결과 수집 후:

1. **충돌 확인**: 전문가 간 상충 정보 식별 (Codex 결과 포함)
2. **교차 검증**: 동일 사실을 2개 이상 전문가가 확인했는지 체크
3. **공백 식별**: 어떤 전문가도 다루지 못한 영역
4. **Codex 합성**: `codex-synthesis.md`의 합성 프레임워크 적용
5. **신뢰도 등급**: 각 주요 발견사항에 신뢰도 부여

신뢰도 등급:

| 등급 | 정의 |
|------|------|
| **High** | 복수 전문가 + 공식 문서로 확인 |
| **Medium** | 단일 소스 또는 간접 확인 |
| **Low / Unverified** | 단일 블로그, 개인 의견, 추정 |

### Step 4: 학습 노트 작성 및 Obsidian 저장

Mode별 출력 형식에 맞춰 정리 후, Obsidian MCP 도구(`obsidian_append_content`)로 직접 저장.

저장 경로: `study/YYYY/MM/<category>/quick/<topic>.md` 또는 `study/YYYY/MM/<category>/deep/<topic>.md`

## 출력 형식

### study 모드 (논리 흐름)

```markdown
# [주제] 학습 노트

**학습일**: YYYY-MM-DD
**목적**: [Purpose]
**모드**: study

---

## 1. 개념 (What)
- 핵심 정의와 용어 정리
- 한 줄 요약

## 2. 배경 (Why)
- 어떤 문제를 해결하기 위해 등장했는가
- 이전에는 어떻게 했는가

## 3. 동작 원리 (How)
- 내부 구조와 메커니즘
- 데이터 흐름 / 처리 과정

## 4. 한계와 대안 (Limits)
- 알려진 제약사항
- 대안 기술과 비교
- 언제 다른 걸 써야 하는가

## 5. 참고 자료
- [제목] (출처, 날짜) — [URL]
```

## 제약사항

- 기존 research와 동일한 신뢰도 원칙 유지 (출처 명시, 공식 문서 > 논문 > 블로그 > 커뮤니티)
- 유료 콘텐츠(강의, 책)는 제목/링크/요약만 수집. 내용 임의 추정 금지
- 2년 이상 된 자료는 날짜 명시 + "현재와 다를 수 있음" 표시
- 버전 명시가 중요한 기술은 반드시 버전 포함
- Obsidian 저장 실패 시 fallback으로 `docs/study/` 경로에 파일로 저장

---

## 트러블슈팅

- **주제가 너무 광범위**: "어떤 측면에 집중할까요?" 범위 좁히기 요청
- **학습 자료가 거의 없는 비주류 주제**: GitHub 소스코드, 이슈, PR을 직접 분석해서 자료 보완. 자료 부족을 명시
- **한국어 자료 필요 시**: 네이버/카카오/라인/토스 기술 블로그, 한국어 번역 문서 우선 조사
- **study와 deep-study 중 모드 선택이 애매할 때**: 주제 복잡도 기준으로 추천하되 사용자 확인
- **Obsidian vault 연결 안 됨**: 사용자에게 알리고 `docs/study/` fallback 경로로 저장

## 검증 방법

- 간단한 주제로 study 모드 테스트 (예: "REST API")
- 복잡한 주제로 deep-study 모드 테스트 (예: "Transformer 아키텍처")
- Obsidian vault 저장 확인
- 카테고리 자동 분류 정확도 확인
