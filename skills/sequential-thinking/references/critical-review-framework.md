# 비판적 검토 프레임워크 (Critical Review Framework)

설계, 계획, 아키텍처 등 의사결정 산출물을 5가지 관점에서 체계적으로 검증한다.

## 적용 시점

- 설계/아키텍처 확정 직전 (최종 검증)
- 중대한 기술 의사결정 후 (ADR 작성 전)
- 기존 설계를 재평가할 때
- 사용자가 "비판적 검토", "약점 분석", "반대 의견 검토" 등을 요청할 때

## 5단계 검토 프로세스

### 1단계: 주요 비판 시나리오 가정 (Devil's Advocate)

설계에 대한 부정적 피드백 3-5가지를 가정하고, 각각에 대응책을 제시한다.

**작성 패턴:**
```
### 비판 N: "[가상의 비판 1줄]"

**핵심**: 이 비판이 왜 타당한지 (가능한 공격 벡터)
**현재 대응**: 설계에 이미 포함된 완화 요소 (있으면)
**추가 보완**: 추가로 필요한 조치
```

**비판 도출 기법:**
- 극단적 시나리오 가정 ("데이터가 100배 늘어나면?", "팀원이 모두 바뀌면?")
- 역할 전환 ("PM이 본다면?", "신규 개발자가 본다면?", "보안 감사자가 본다면?")
- 시간 축 이동 ("6개월 후에도 유효한가?", "3년 후에도 유지보수 가능한가?")

### 2단계: 다각적 분석과 반대의견 검토

최소 2-3가지 관점에서 설계를 재해석하고, 반대의견을 논리적으로 반박 또는 수용한다.

**표준 분석 관점:**

| 관점 | 검토 질문 |
|------|-----------|
| 성능 (Performance) | 병목은 어디인가? 스케일링 시 어떻게 되는가? |
| 보안 (Security) | 공격 표면은? 데이터 유출 경로는? |
| 유지보수성 (Maintainability) | 6개월 후에도 이해 가능한가? 변경 비용은? |
| 확장성 (Scalability) | 요구사항이 2배/10배 되면? |
| 비용 (Cost) | 시간/리소스/금전적 비용은 적정한가? |
| 사용자 경험 (UX) | 사용자에게 부담을 주지 않는가? |

> 모든 관점을 다 적용할 필요는 없다. 설계 성격에 따라 관련 관점 2-3개를 선택.

**작성 패턴:**
```
### 관점 X: [관점명]

**분석**: 이 관점에서 설계의 현재 상태
**반대의견**: "~하면 되지 않는가?" 형태의 대안 주장
**반박/수용**: 반대의견이 틀린 이유 또는 수용할 부분
**결론**: 변경 필요 여부
```

### 3단계: 잠재 오류·편향 점검

설계 과정에서 발생할 수 있는 인지 편향과 논리적 오류를 점검한다.

**점검 대상 편향 목록:**

| 편향 | 증상 | 질문 |
|------|------|------|
| Anchoring Bias | 첫 번째 수치/기준에 과도하게 의존 | "이 수치의 근거는 무엇인가?" |
| Confirmation Bias | 자기 결정을 지지하는 증거만 수집 | "반대되는 증거를 찾아보았는가?" |
| Tool Familiarity Bias | 익숙한 기술을 선호 | "다른 기술이 더 적합한 경우는?" |
| Sunk Cost Fallacy | 이미 투자한 비용 때문에 지속 | "지금 시작한다면 같은 선택을 하겠는가?" |
| Complexity Bias | 복잡한 솔루션이 더 좋다고 가정 | "더 단순한 대안은 없는가?" |
| Survivorship Bias | 성공 사례만 참조 | "실패 사례에서 배울 점은?" |
| IKEA Effect | 자기가 만든 것에 과대 평가 | "외부인이 보면 어떻게 평가하겠는가?" |

**작성 패턴:**
```
### 편향 N: [편향명]

**현상**: 설계에서 이 편향이 나타나는 지점
**개선**: 편향을 제거하거나 완화하는 방법
```

### 4단계: 근거와 출처 명시

설계안의 각 결정을 뒷받침하는 근거를 명시한다.

**근거 유형 (신뢰도 순):**
1. 공식 기술 문서 (RFC, 공식 docs, 프레임워크 가이드)
2. 업계 표준/가이드 (Microsoft WAF, AWS Well-Architected, Google SRE)
3. 학술 논문/서적 (peer-reviewed)
4. 업계 블로그/컨퍼런스 발표 (ThoughtWorks, InfoQ, 주요 기업 엔지니어링 블로그)
5. 커뮤니티 합의 (Stack Overflow, GitHub discussions)
6. 개인 경험 (명시적으로 "경험적 판단"으로 표기)

**작성 패턴:**
```
| 설계 요소 | 근거 | 출처 |
|-----------|------|------|
| [결정 사항] | [왜 이것이 맞는지] | [URL 또는 문서명] |
```

> 근거가 없는 결정이 있다면, 해당 결정이 "가정"임을 명시하고 검증 방법을 제안한다.

### 5단계: 결론 및 추가 점검

**산출물:**
1. 설계의 핵심 강점 요약 (3줄 이내)
2. 식별된 개선 항목 (우선순위순 테이블)
3. 놓친 이슈 점검 (환경별, 시간축별, 팀 구성별)

**개선 항목 테이블 포맷:**
```
| # | 개선 항목 | 심각도 | 조치 |
|---|-----------|--------|------|
| 1 | [항목] | High/Medium/Low | 수정 필요 / 선택적 |
```

**놓친 이슈 점검 질문:**
- 다른 환경(OS, 클라우드, 온프렘)에서도 동작하는가?
- 팀 규모가 변하면 영향이 있는가?
- 규제/컴플라이언스 요구사항은 없는가?
- 장애 시 복구 경로(rollback)는 명확한가?
- 모니터링/관측성(observability)은 고려되었는가?

## 검토 강도 조절

| 설계 규모 | 검토 강도 | 적용 단계 |
|-----------|-----------|-----------|
| Small (단일 컴포넌트) | 경량 | 1단계(비판 2-3개) + 4단계(근거) |
| Medium (복수 모듈) | 표준 | 1-4단계 전체 |
| Large (시스템 수준) | 심층 | 1-5단계 전체 + 외부 레퍼런스 검색 |
